## C. Why necessary

Ownership is not implementation evidence. A successful page load cannot establish required state transitions or persistence. Child scope may be incomplete without invalidating a legitimate foundation's own file obligations; parent completeness must retain the full source set.

## D. Root cause

Generic web-profile evidence lacks task-specific assertions; optional browser applicability can be weaker than the assigned behavior. Ordinary evidence aggregation interpreted actual syntax/load PASS without requiring source-bound executable outcomes. Historical tool output could therefore be reused without independently checking current behavior.

## E. Exact changes

- New `hivo/behavioral_obligations.py`: bounded declarative file-existence and browser-scenario contracts. Source IDs/text must match assigned canonical records. Named-file-only duties need every explicit file; compound content/behavior cannot be reduced to existence. Supported interaction scenarios require a before/action/changed-state assertion; persistence duties require reload. Unknown semantics, unsupported actions, unsafe targets, invalid types or incomplete coverage remain uncovered.
- Browser adapter executes fixed operations (fill/click/check/uncheck/reload and text/value/count/checked/visibility assertions), not generated Python/JS/shell. Uses isolated contexts, a 20-second verification deadline checked between steps, bounded action/navigation/launch waits and controlled local resource serving. Runtime/resource errors fail. External requests are refused. Inspection dependencies must fit already authorized paths; no write permission is granted.
- Capture relevant source fingerprints before/after verification and reject changes. Run the adapter freshly on every bound canonical child gate, including repair rechecks; old completion prose or cached receipts cannot replace it.
- Ordinary planner schema/prompt carries frozen `verification_obligations` and parent obligations. Admit only covered, source-bound plans with valid owner/dependency inspection targets. Invalid oracle planning stops before dispatch instead of falling back to unbound work. Dispatch validates again.
- New unit/gate controls, working/inert controller chains and a real nine-case browser matrix. Existing reports/diagnostics preserved.

## F. Mechanism / alternatives

Canonical source -> scoped requirement owners -> admitted declarative oracle plan -> real execution -> independent current browser/file checks -> before/after subject identity -> deterministic gate -> existing impact audit/commit or bounded repair/rollback. Foundation has file-only duties; downstream behavior stays with the functional child. Every fresh repair gate reruns the same admitted obligations.

Rejected alternatives: regex-checking application JS for handlers, application-specific selectors in production, generated executable verifier code, treating page visibility as behavior, or auto-upgrading old proof. The vocabulary is deliberately narrow; unsupported duties fail closed. Source text equality and capability classification do not prove arbitrary semantic equivalence between prose and a proposed scenario. Controlled scenarios were independently reviewed against their exact source and observable outcomes; broader semantic-oracle reliability is not claimed.
